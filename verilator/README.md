### Configuration

### Deviation from the standard configuration

`DETAILED_PLAN_0.md` lists "a 2x2 mesh for iteration" as the standard
configuration for the whole effort. `N_TILES_X`/`N_TILES_Y` are
`localparam`s hardcoded to 4 in `hw/mesh/magia_pkg.sv` with no existing
override mechanism (define, parameter, etc.). Adding one is an RTL change to
a file shared by all simulators and synthesis, and Plan 1 explicitly
restricts RTL changes to defects the flat compiler exposes in the draft
boundary work. Building a mesh-size override was treated as out of scope for
Plan 1 and left for a future plan if iteration speed becomes a problem;
Plan 1 instead ran the flat flow against the existing default 4x4 mesh.

### Step 1 — inspect existing Make variables

Confirmed with `make -n verilator-bender core=CV32E40P mesh_dv=1` that
`BENDER` resolves to the literal `bender` on this host, and that
`bender_targs`/`bender_defs` (built up across `bender_common.mk`,
`bender_sim.mk`, `bender_synth.mk`, `bender_profile.mk`, and the core/Spatz
`ifeq` blocks in `Makefile`) are fully populated by the time
`verilator/verilator.mk` is included at the bottom of `Makefile`. No changes
needed here; the rewritten `verilator.mk` reuses `$(bender_targs)` and
`$(bender_defs)` unchanged, only adding Verilator-specific targets/defines
on top, as required.

### Step 2 — normalize and validate the file list

Rewrote `$(VERILATOR_BUILD_DIR)/magia.raw.f` (raw Bender output, one shared
file regardless of `mesh_dv`) → `$(VERILATOR_FLAT_DIR)/magia.f` (filtered,
checked, atomically installed) as two real Make targets instead of the
previous `sed -i` chain run unconditionally inside one recipe.

**Found and fixed a real file-list defect** (this is a build-list/Makefile
correctness issue, not the RTL hierarchy-boundary defect Plan 1 defers to
Plan 2 — see below): the previous `verilator.mk` resolved the DPI
`remote_bitbang`/`sim_jtag` C sources via `$(BENDER) path cv32e40p)`, but
those files actually live under the `riscv-dbg` Bender package
(`riscv-dbg/tb/remote_bitbang/{sim_jtag,remote_bitbang}.c`); the
`cv32e40p` checkout has no `tb/dm/remote_bitbang` directory at all. This was
silently wrong before because nothing checked it — `check_filelist.py`
(new in the draft) caught it immediately as "missing source files". Fixed by
resolving `RISCV_DBG_ROOT := $(shell $(BENDER) path riscv-dbg)` instead.

Also fixed: the old recipe appended both DPI C files on a single
space-joined line (`echo $(VERILATOR_DPI) >> $@`), which `filter_filelist.py`
would have treated as one bogus non-existent path. Now each DPI source is
appended on its own line.

`filter_filelist.py`/`check_filelist.py` were present as an untracked draft
but used `from __future__ import annotations` and PEP 585 generics
(`set[str]`, `list[str]`) as variable annotations — both require Python
≥3.7/3.9. `BASE_PYTHON` on this host resolves to `/usr/bin/python3`
(3.6.8, no `/etc/iis.version`), so both scripts raised `SyntaxError` before
running at all. Removed the future import and the bare-generic annotations
(kept the scripts' logic identical) so they run under 3.6+.

File-list generation now has real prerequisites: `Bender.yml`, `Bender.lock`,
a Bender version/path stamp (`verilator/build/.bender-version`, updated
atomically only when the resolved binary or its `--version` output changes),
and the two helper scripts.

### Step 3/4 — build configuration controls and split targets

Added `VERILATOR_JOBS` (validated as a positive integer via
`expr $(VERILATOR_JOBS) + 0`, avoiding literal `()` inside `$(shell ...)`
which broke Make's own paren matching in an earlier draft of this rule),
`VERILATOR_TRACE`, `VERILATOR_TRACE_STRUCTS`, `VERILATOR_TRACE_PARAMS`
(both rejected with `$(error ...)` when `VERILATOR_TRACE=0`), and
`VERILATOR_CFLAGS`. `--trace-fst` is only added when `VERILATOR_TRACE=1`;
`--trace-structs`/`--trace-params` are separate opt-ins under that gate.
Replaced the hardcoded `-j 0` with `-j $(VERILATOR_JOBS)`.

Split into explicit targets in `verilator/verilator.mk`:

- `verilator-bender` → `$(VERILATOR_FLAT_DIR)/magia.f`
- `verilate-flat-gen` → `$(VERILATOR_FLAT_OBJ_DIR)/V$(tb).mk` (Verilator
  `--cc --main --exe`, generation only — `--binary` does not expose a seam
  between codegen and native build in this Verilator version, so switched to
  `--cc --main --exe` followed by an explicit `make -C obj_dir -f V$(tb).mk`
  as the plan allows)
- `verilate-flat-build` → `$(VERILATOR_FLAT_OBJ_DIR)/V$(tb)` (native build,
  `$(MAKE) -C ... -j $(VERILATOR_JOBS)`)
- `verilate-flat` → alias for the above, plus the existing `VERILATOR_PATH`
  hint
- `verilate` → temporary alias for `verilate-flat` (per Plan 0, do not
  switch this to hierarchy before Plan 5's adoption gates pass)
- `clean-verilate-flat` → removes only `$(VERILATOR_FLAT_DIR)`, never wired
  into `verilate`'s dependency graph

`mesh_dv=1` (default mesh) builds under `verilator/build/flat/`, so the
executable path is `verilator/build/flat/obj_dir/Vmagia_tb` as required.
`mesh_dv=0` (standalone tile) builds under the separate
`verilator/build/flat-tile/` directory with top `magia_tile_tb`, so the two
configurations cannot overwrite each other.

### Step 5 — configuration stamp

### Blocking failure (defect in the draft Phase-1 boundary work, deferred to Plan 2)

Command:

```
make verilate-flat-gen core=CV32E40P mesh_dv=1 VERILATOR_JOBS=4
```

First useful error:

```
%Error: hw/tile/magia_tile.sv:151:47: Can't find definition of 'ex_valid' in dotted variable/method: 'i_cv32e40p_ctrl_core.ex_valid'
  151 |     observe_o.instr_ex = i_cv32e40p_ctrl_core.ex_valid ?
      |                                               ^~~~~~~~
%Error: hw/tile/magia_tile.sv:152:47: Can't find definition of 'id_stage_i' in dotted scope/variable: 'i_cv32e40p_ctrl_core.id_stage_i'

```

`hw/tile/magia_tile.sv:137-159` populates the new `observe_o` port for the
CV32E40P case with dotted hierarchical reads several levels into
`i_cv32e40p_ctrl_core`'s internals (`ex_valid`, `id_stage_i.instr_rdata_i`,
`wb_valid`, `instr_rdata_id`, `regfile_wdata`) — signals that actually live
one level deeper, under `i_cv32e40p_ctrl_core.cv32e40p_top_i`, per
Verilator's own "Known scopes" hint. This is precisely the anti-pattern
`PLAN.md` Phase 1 calls out and prohibits: *"Do not use `public_flat`, VPI,
or dotted paths as a substitute [for the observation port]; those would
recreate coupling to child implementation details."* The CV32E40X branch of
the same `always_comb` block (lines 144-149) has the same shape and is
equally unvalidated (it was not reached because Verilation fails on the
CV32E40P branch first, and `core=CV32E40P` is Plan 0's standard
configuration).

Per `DETAILED_PLAN_1.md`: *"Do not change RTL to solve this phase unless the
flat compiler exposes a real RTL defect from the draft boundary work. Such a
defect belongs to Plan 2 and must be documented there."* This is exactly
that situation, so `hw/tile/magia_tile.sv` was intentionally left unmodified.
The fix belongs to `DETAILED_PLAN_2.md`'s observation-port work: route the
needed EX/ID/WB instruction and writeback-data signals out through
`magia_tile`'s own ports (or the CV32E40P core wrapper) instead of reading
into `i_cv32e40p_ctrl_core` by dotted name, then populate `observe_o` from
those local signals.

The failure is deterministic and independent of the Makefile changes above:
reproduced twice from a clean `verilator/build/flat/` with an identical
`magia.f`.

### Step 1 — validate the observation type

Read the pre-refactor `magia_vip.sv`/`magia_tile_vip.sv` (via
`git show HEAD:...`) to recover the exact historical semantics of every
signal the old testbenches read by dotted path, then checked the draft
`magia_tile_observe_t` (`hw/tile/magia_tile_pkg.sv`) against it field by
field:

- print (`axi_aw_addr`/`axi_aw_id`/`axi_aw_valid`/`axi_w_data`/`axi_w_valid`):
  matches the old `i_axi_xbar.mst_ports_req_o[0]` reads exactly.
- `instr_ex`/`instr_id` (`PROFILE_DETAILED`): matches the old
  `curr_instr_ex`/`curr_instr_id` continuous assigns exactly, including the
  CV32E40P `ex_valid`-gated zeroing behavior and the ungated ID-stage tap.
- `instr_wb` vs `wb_data`: the old mesh VIP used **two different physical
  signals** under the same local name `curr_instr_wb` in two mutually
  exclusive `` `ifdef `` blocks — `PROFILE_SENTINEL` reads
  `wb_valid ? instr_rdata_id : '0` (the raw instruction word), while
  `PROFILE_SYNC` reads `wb_valid ? regfile_wdata : '0` (the register
  write-back **data**, which for the sentinel `addi` instructions happens
  to equal the same magic constants by construction). The draft struct
  already had two distinct fields (`instr_wb` for the former, `wb_data` for
  the latter) and the current `magia_vip.sv` already reads the correct
  field in each `` `ifdef `` block — this was already correct, no change
  needed here.

**Found and fixed a real width bug**: `axi_aw_id` was declared
`logic [AXI_ID_W-1:0]`, i.e. sized from `magia_tile_pkg::AXI_ID_W` (3 bits
— the width of the tile's *internal* 5-port OBI/AXI crossbar). The signal
it is actually driven from,
`axi_xbar_mst_req[AXI_MST_OBI_IDX].aw.id`, is typed
`magia_pkg::axi_xbar_mst_req_t` (the NoC-facing crossbar, aliased from
`noc_axi_data_req_t` via `` `AXI_ALIAS ``), whose ID width is
`magia_pkg::AXI_NOC_ID_W` = 6 bits — a completely different xbar. Fixed by
sizing the field from `magia_pkg::AXI_NOC_ID_W` instead, with a comment
explaining why the tile package's own `AXI_ID_W` must not be reused here
(`hw/tile/magia_tile_pkg.sv`).

### Step 2 — validate `magia_tile.observe_o`

This is what was blocking Plan 1. Root-caused by reading the actual
third-party IP sources rather than guessing from Verilator's error text:

- `Bender.yml` unconditionally sets `CORE_TRACES: ~` for every `magia_dv`
  target (both the mesh and `standalone_tile` source sets), so
  `CORE_TRACES` is **always** defined for this Verilator flow — there is no
  way to disable it without a Bender.yml change. That means the
  `` `ifndef CORE_TRACES cv32e40p_top #(...) `else cv32e40p_wrapper #(...) ``
  branch in `magia_tile.sv` always selects `cv32e40p_wrapper`, not
  `cv32e40p_top` directly.
- `cv32e40p_wrapper` (`.bender/git/checkouts/cv32e40p-*/bhv/cv32e40p_wrapper.sv`)
  instantiates `cv32e40p_top` as `cv32e40p_top_i` — exactly the scope name
  Verilator's error hint reported (`Known scopes under
  'i_cv32e40p_ctrl_core': cv32e40p_top_i`).
- `cv32e40p_top` in turn instantiates `cv32e40p_core` as `core_i`, which is
  where `ex_valid`, `wb_valid`, `id_stage_i`, `instr_rdata_id`, and
  `regfile_wdata` actually live (confirmed by grepping
  `cv32e40p_core.sv` directly).
- The draft's CV32E40P dotted paths were missing this
  `.cv32e40p_top_i.core_i.` prefix (the CV32E40X branch already had the
  equivalent `.core_i.` — CV32E40X's `cv32e40x_wrapper` instantiates
  `cv32e40x_core` directly as `core_i`, one level shallower, which is why
  only the CV32E40P branch broke). Fixed all four assignments in
  `hw/tile/magia_tile.sv:150-161`; added a comment recording the wrapper
  chain so the next person doesn't have to re-derive it from a Verilator
  error message.
- Cross-checked the CV32E40X branch by reading `cv32e40x_core.sv` directly
  (`id_stage_i`/`wb_stage_i` instance names and
  `if_id_pipe_i`/`id_ex_pipe_o`/`ex_wb_pipe_i` port names all match the
  existing dotted path) — structurally correct as written, but **not
  exercised by an actual CV32E40X compile** in this session (see Step 6).

This is internal-to-the-tile dotted access (`magia_tile.sv` reading its own
`cv32e40p_top`/`cv32e40p_core` submodule instances), not a hierarchy-block
boundary crossing — `magia_tile` itself is never marked `hier_block`, only
the thin `magia_tile_hier` wrapper is. Verilator rejected it purely because
the path was one level too shallow, not because dotted references are
disallowed here; Plan 2's prohibition on dotted paths is about the
mesh/testbench reading into the tile from *outside*, which Step 5 covers
separately.

Single driver: the whole `observe_o` assignment is one `always_comb` block;
no combinational loop (verified by successful Verilation, which would flag
`UNOPTFLAT`/combinational-loop errors — none were raised for this signal).

### Step 6 — first successful build: three real defects and one deep Verilator bug

This step is where nearly all of the effort in this phase went. Each
failure below was fully root-caused (not worked around blindly) before
being fixed, because several of them looked superficially similar
("something about the hierarchy boundary is wrong") but had unrelated
causes.

**Defect 1 (MAGIA RTL): enum-package-typed parameters on the hier_block.**
`magia_tile_hier.sv`'s `CORE_ISA`/`CORE_A`/`CORE_B`/`CORE_M`/`ERROR_CAP`
parameters were typed `cv32e40x_pkg::rv32_e` /
`cv32e40x_pkg::a_ext_e`/`b_ext_e`/`m_ext_e` / `idma_pkg::error_cap_e`.
Verilator's hierarchical Verilation only accepts integer/floating
point/string/type parameters on a `hier_block`; package-scoped enum types
are rejected even when never overridden (first error:
`'magia_tile_hier' has hier_block metacomment, hierarchical Verilation
supports only integer/floating point/string and type param parameters`).
Fixed by declaring these as plain `logic`/`logic[1:0]` parameters sized to
match each enum's own base type (checked directly against each enum's
`typedef enum logic ... {...}` in the relevant IP package — `rv32_e` and
`error_cap_e` are 1 bit, `a_ext_e`/`b_ext_e`/`m_ext_e` are 2 bits), keeping
the identical default values, and casting back to the real enum type
(`cv32e40x_pkg::rv32_e'(CORE_ISA)` etc.) only at the `magia_tile`
instantiation inside the wrapper. No behavior change for any simulator —
this is a parameter *type* change at one boundary, not a value change.

**Defect 2 (MAGIA RTL): empty-parens parameter overrides.** `magia.sv`'s
`magia_tile_hier` instantiation had
`.CORE_ISA ( ), .CORE_A ( ), .CORE_B ( ), .CORE_M ( ), .ERROR_CAP ( )` —
explicit-but-empty parameter connections, meaning "use the default,"
inherited unchanged from the pre-hierarchy code. This continued to error
even after Defect 1's type fix (same error, unchanged), independent of
parameter type: hierarchical Verilation rejects the empty-parens override
syntax outright. Since all 16 default-mesh tiles already use identical
(default) values for these five parameters — consistent with PLAN.md's
explicit one-specialization assumption — the correct fix was to drop them
from the override list entirely rather than find a non-empty way to
re-assert the default.

**Defect 3 (Bender file list, both flat and hier): an unreachable
testbench file that Verilator only chokes on in hierarchical child mode.**
Once Defects 1–2 were fixed, the top-level plan succeeded and Verilator
began Verilating the `magia_tile_hier` child in its own isolated
sub-invocation — and hit
`` `ASSERT(RequestProgress, dut_valid |-> ##[0:RequestTimeout] dut_ready, clk, rst) ``
in `.bender/git/checkouts/cluster_icache-*/test/snitch_icache_l0_tb.sv`
(`Unsupported: ## range cycle delay range expression`). This file is a
standalone testbench for `snitch_icache_l0`, pulled into the source list
by a broad Bender target, never instantiated by `magia_tb`/`magia_tile_tb`
— exactly like the five files Plan 1 already excludes. The **flat** build
never even attempts to fully parse it, because nothing reachable from the
design instantiates it and Verilator's flat elaboration is lazy about
unreached modules; a hierarchical **child**'s own sub-invocation appears
to parse more eagerly and hits the unsupported construct directly. Added
`snitch_icache_l0_tb.sv` to the `EXCLUDED`/`UNSUPPORTED` sets in
`verilator/filter_filelist.py` and `verilator/check_filelist.py` (now six
documented exclusions, not five — flagged here since several docstrings/
Detailed Plan 1 refer to "the five documented files"). This is shared
infrastructure, so it affects `verilate-flat` too (harmlessly — the file
was dead code there).

**Defect 4 (Verilator 5.046 itself, worked around not patched): two
independent, source-confirmed argument-propagation bugs in hierarchical
child re-invocation.** After Defect 3, the child's own sub-invocation
still failed — first on `common_cells/registers.svh` (a self-referential
`` `include "common_cells/registers.svh" `` needing an incdir that *is*
present in `$(VERILATOR_FLIST)`). Root-caused by reading
`/sw/tool/verilator/v5.046/src/V3HierBlock.cpp`'s
`writeCommandArgsFile()` and `/sw/tool/verilator/v5.046/src/V3Options.cpp`'s
`allArgsStringForHierBlock()`:

1. When Verilator regenerates a hierarchical child's own re-invocation
   command, it reconstructs it from `m_impp->m_lineArgs` — the **literal
   original argv tokens** the top-level invocation was called with — not
   from the expanded contents of any `-f` file. `+define+`/`+incdir+`
   lines embedded inside `$(VERILATOR_FLIST)` are therefore invisible to
   every child sub-invocation, confirmed by inspecting the regenerated
   `V<mangled>__hierMkArgs.f`: zero `+define`/`+incdir` tokens, even though
   the top-level invocation's *own* elaboration (which reads `-f`
   normally) had no trouble with them. **Fix:** pass every `+define+`/
   `+incdir+` token from `$(VERILATOR_FLIST)` a second time, literally on
   the command line, alongside `-f $(VERILATOR_FLIST)` — this is exactly
   what `allArgsStringForHierBlock()` is designed to forward (its filter
   logic explicitly special-cases and strips `-`-prefixed tool options and
   known source-file paths, but has no special case for `+`-prefixed
   tokens, so they fall through and are preserved).
2. Supplying those tokens on the command line initially traded the missing
   include for a much worse failure: `%Error: Internal Error:
   ../V3LinkCells.cpp:906: top module must be listed in
   --hierarchical-block`, but only once "enough" flags were present for
   the design to actually progress to real linking (confirmed by bisecting
   the incdir set — 1, 16, 25, 30, 32 of 33 all failed on an ordinary
   missing-include error and never reached this assertion; only the full,
   correct set did, because only then does `hw/include` let
   `magia_pkg.sv` itself parse). Reading
   `V3LinkCells.cpp:895-907` and `V3Options.cpp`'s option table pinned the
   exact cause: `stripOptionsForChildRun()`'s `commonOpts` map strips
   `--top-module` (2 tokens) from the reconstructed child command line but
   has no entry for its exact synonym `--top` (`-top` and `-top-module`
   are registered as identical callbacks in `V3Options.cpp:1798-1801`, both
   setting `m_topModule`). The stray `--top magia_tb` from *our own*
   top-level invocation therefore always survives into every child's
   regenerated args file and, parsed *after* the correct
   `--top-module-encoded <mangled-name>`, silently overwrites it — so by
   the time `V3LinkCells`'s hierarchical-child visitor looks up
   `v3Global.opt.topModule()` in the (mangled-name-keyed, per
   `V3Options.cpp:1520`) hierarchical-block map, it's looking up `magia_tb`
   instead of `magia_tile_hier_f`, which is never in that map. **Fix:**
   invoke our own top-level command with `--top-module magia_tb` instead
   of `--top magia_tb` — same effect on our invocation (documented
   synonym), but it *is* in the strip list, so it never leaks into child
   reconstruction in the first place.

With both fixes applied, the child Verilated cleanly in 56 s (versus 942 s
for the equivalent scope inside the full flat build — a first, informal
signal that the partitioning is doing something real, not yet a Plan 4
measurement), and the top-level parent build completed afterward without
further incident.

This qualifies as "a specific, documented 5.046 limitation... reproduced
with a minimal case" per Plan 3's own criterion for when a fallback is
justified — except a full workaround was found (`--top-module` +
literal-CLI flag duplication), so no fallback to manual `--lib-create` was
needed. Both fixes are implemented in `verilator/verilator.mk`
(`VERILATOR_HIER_FLIST_FLAGS`, and `--top-module` in the codegen recipe),
with the full derivation captured in comments there pointing back to this

### Step 2 — source dependency wiring

**Found a real gap while implementing this step**: before this change,
`$(VERILATOR_FLAT_MK)`/`$(VERILATOR_HIER_MK)` only depended on the
normalized file *list* and the config stamp — editing an RTL file's
*content* in place, without touching `Bender.yml`/`Bender.lock`/any define,
would not have been noticed by Make at all.

Fixed by `-include`ing Verilator's own generated dependency files:

- Flat: `-include $(VERILATOR_FLAT_OBJ_DIR)/V$(tb)__ver.d`. This file's
  rule LHS is exactly `$(VERILATOR_FLAT_MK)` (e.g. `Vmagia_tb.mk`), so GNU
  Make's standard prerequisite-merging applies directly. Verified working
  (a real RTL touch is correctly seen as a reason to rebuild).
- Hier: `-include $(VERILATOR_HIER_OBJ_DIR)/V$(VERILATOR_HIER_TOP)__hierVer.d`.
  This aggregate file (covers both parent and child RTL/include sources,
  confirmed by grep) has a rule LHS naming the *parent's own byproduct*
  (`$(VERILATOR_HIER_PARENT_MK)`, e.g. `Vmagia_tb.mk`), not the top-level
  hierarchy driver (`$(VERILATOR_HIER_MK)`, e.g. `Vmagia_tb_hier.mk`) that
  `verilate-hier-gen` actually targets — even though one
  `verilator --hierarchical` invocation produces both files. Declaring
  both as a single grouped-target rule (`&:`, GNU Make 4.3+) was tried
  first, to let the `-include`d prerequisites apply to the whole recipe;
  it produced inconsistent staleness decisions (see the open issue below)
  and was reverted to a classic multi-target rule
  (`$(VERILATOR_HIER_MK) $(VERILATOR_HIER_PARENT_MK): deps...`), which is
  unaffected by the classic multi-target/parallel-build caveat since
  nothing in this Makefile ever requests both as separate `-j` goals.

### Open issue: hier codegen target shows spurious/inconsistent staleness

**Not resolved. Documented here rather than further chased, per explicit
instruction partway through this phase to stop triggering additional full
rebuilds to debug it.**

Symptom: after the Step 1 stamp-format change forced one legitimate,
one-time rebuild (expected — the stamp's *content* genuinely changed),
`$(VERILATOR_HIER_MK)`/`$(VERILATOR_HIER_PARENT_MK)` did not "catch up" to
`config.stamp`'s new mtime the way `verilate-flat`'s equivalent did
earlier in this project (Plan 1/2/3 hit and fixed the same underlying
pattern for the flat file-list targets: Verilator's own internal freshness
check can decide "nothing to regenerate" and, in that case, does not
appear to touch the output file's mtime, so a target can stay
permanently "older than" a prerequisite whose *content* has stopped
changing). The standard fix used elsewhere in this project — a one-time,
content-neutral `touch` bringing the stuck target's mtime forward — was
applied here too, and confirmed via direct `stat` that
`Vmagia_tb_hier.mk`'s mtime (10:20:27) is unambiguously newer than
`config.stamp`'s (10:15:28). Despite that, `make -d -n verilate-hier-gen`
immediately afterward still reports `config.stamp' is newer than target
'.../Vmagia_tb_hier.mk'` and decides to remake it. The two pieces of
evidence directly contradict each other and the discrepancy was not
explained before work stopped on it — possibly an NFS timestamp
caching/precision artifact on this host (`/srv/home/...` is a network
filesystem), possibly a genuine Make dependency-graph interaction with the
`-include`d hier dependency file that the multi-target revert did not
fully resolve. **Not extracted: a confirmed root cause.**

Practical impact, as best determined without further rebuilds: any
spurious reinvocation this causes is cheap, not a real rebuild — Verilator
was independently confirmed (`Vmagia_tb__pch.h.fast.gch` etc. and Plan 3's
own no-op timing signature, "Built from 0.000 MB sources in 0 modules,"
elapsed ~0.03 s) to internally detect when nothing needs regenerating and
skip real work even when its own recipe is re-invoked. So the risk is
wasted milliseconds re-checking, not wasted minutes rebuilding — but Plan
4's exit criterion ("a second no-change `make verilate-hier` performs no
compilation and no link") is not confirmed to hold in the strictest sense
(zero recipe invocations) for the hier path specifically, only in the
weaker sense (no real compiler/linker work). **Whoever picks this up next
should re-run `make -d -n verilate-hier-gen` after a clean, from-scratch
hier build (no intervening stamp-format changes) to see whether the
discrepancy reproduces from a pristine state, before assuming it is an
NFS artifact.**

### Steps 3-4 — invalidation tests

`verilator/invalidation_test.sh` was written, covering all required
scenarios: no-change no-op, mesh/VIP-only touch (parent rebuilds, child
library untouched), tile RTL touch (child rebuilds, executable relinks),
Spatz define change (compatible rebuild + revert), control-file touch,
DPI-source touch, and a simulated stale-version stamp (Step 4's
alternative to installing a second Verilator). It uses only `touch`/
`touch -d @<epoch>` for mtime manipulation, restores every file it
touches, and asserts on artifact mtimes/existence rather than log text.

An earlier run had every scenario fail, but was not trustworthy evidence
of a real defect: it executed while the codegen recipe was re-running on
every `make` call regardless of what the test touched, which confounds
every mtime-based assertion the script makes.

**That blocker is fixed** (see "Planner convergence" below), and the suite
has now been run for the first time against a confirmed zero-recipe no-op
baseline. Note the suite needs a `VERILATOR_JOBS=4` build to exist first:
the job count is inside `verilator_args` in `config.stamp`, so a baseline
built with any other value fails test 1 for that reason alone.

Result: **6 of 8 pass** — 1 (no-change no-op), 4a/4b (Spatz define change
and revert), 5 (control-file touch), 6 (DPI-source touch), 8 (simulation
main edit).

**Tests 2 and 3 fail, and the cause is not stale reuse in this Makefile.**
Both change only mtimes. The codegen rule *does* re-invoke Verilator on
the touched input — the logs show exactly one
`magia_hier.vlt --hierarchical` — but Verilator 5.046 checks source
*content* (`Vmagia_tb__hierVer.d`, `*.verilator_deplist`) and returns in
0.027 s reporting "Built from 0.000 MB sources in 0 modules", so nothing
is regenerated, nothing recompiles, and nothing relinks. The two tests
encode a "touch implies rebuild" contract the toolchain deliberately does
not provide; test 5 passes on the same kind of touch only because it
asserts on the plan's mtime rather than on downstream artifacts. Rewrite
them around content changes (as test 8 does) before treating a failure
here as a build defect.

#### Planner convergence

The codegen rule ends with `@touch $(VERILATOR_HIER_MK)`. Verilator's
planner has its own dependency check and leaves that file alone when the
plan itself has not changed, so any prerequisite that is merely newer — a
rewritten `config.stamp`, say — otherwise left the target permanently out
of date and re-ran Verilator on every subsequent `make`, forever. This is
what made the no-change no-op unattainable and the suite unusable.
Touching the rule's own target converges it. This is
`V$(VERILATOR_TOP)_hier.mk`, *not* the stage-2 product
`V$(VERILATOR_TOP).mk`, which must never be touched here for the reason
documented at that rule.

### Step 5 — object cache

No integration work needed: Verilator's generated Makefiles already invoke
`$(OBJCACHE) $(CXX) ...` for every compile unit, and `ccache` (present on
this host, version 3.7.7) is auto-detected with no Makefile-side wiring —
confirmed by seeing `ccache g++ ...` in every build log without this
project ever mentioning `ccache` before this check. `config.stamp` now
records which cache tool (if any) was resolved, satisfying the
"[include] the selected cache tool in configuration identity" requirement
without changing build behavior. Comparing invalidation-test timing with
caching on vs off was not done, since it requires the Step 3-4 test suite
to be trustworthy first (see above) and was explicitly deprioritized: "Only
after every invalidation test passes."

### Step 6 — clean-target safety

**Found and fixed a real bug**: `clean-verilate-hier` was defined inside
the same `ifeq ($(mesh_dv),0) ... error ... else ...` guard as the
build/check targets, so `make clean-verilate-hier mesh_dv=0` incorrectly
hard-errored — even though `$(VERILATOR_HIER_DIR)` does not depend on
`mesh_dv` at all (only *building* hier output requires `mesh_dv=1`;
cleaning it does not need any design-configuration context). Moved its
definition out to be unconditional, keeping only the true build/check
targets behind the guard.

All three clean targets were verified with sentinel files:
`clean-verilate-flat` removes only its own directory, leaves a sibling
flat-tile marker and the shared build root untouched; `clean-verilate-hier`
removes only its own directory; `clean-verilate-all` removes both and
leaves the build root itself in place. **This verification was redone in
an isolated scratch tree** (`VERILATOR_BUILD_DIR` override to a
`/tmp` scratch path) after an initial mistake running the identical test
against the real, live build directories while a background rebuild
(`bivg8p7do`) was still writing into `verilator/build/flat` — the `rm -rf`
deleted the directory out from under the running process. The background
process survived (its recipe's `mkdir -p`/Verilator's own directory
creation recreated the tree) and a follow-up no-op `make verilate-flat`
plus an ELF sanity check (`file(1)`) confirmed the resulting binary was not
corrupted, but this was a real close call worth recording: **clean-target
tests must always run against an isolated `VERILATOR_BUILD_DIR`, never the
live build tree**, especially with background builds in flight.

## Cleanup phase: hierarchy-only flow, and the flat-parent defect

Plans 5/6 were superseded by `DETAILED_PLAN_CLEANUP.md`. The flat mesh flow is
intentionally gone: `verilate` aliases `verilate`, everything lives under
`verilator/build`, and Verilator-only sources live in
`target/verilator/src` (`magia_tile_hier.sv`, `magia_vip.sv`,
`magia_fixture.sv`) with shared RTL differing only inside small
`` `ifdef VERILATOR `` branches.

### The build reported success while producing a flat model

`make verilate` built, archived and linked `libmagia_tile_hier_f.a` and
`verilate-check-hierarchy` passed — while the parent Verilated all 16 tiles
inline. Evidence at the time: 2149 parent `.cpp` files (the flat baseline above
is 2152), 451 `cv32e40p` and 344 `magia_tile_hier__N20_NB2000` entries in
`Vmagia_tb_classes.mk`, zero references to the child library, 894 s and 18.5 GB
for the parent alone. Two independent causes:

**1. Verilator 5.046 silently skips hier_block substitution without
`--hierarchical-params-file`.** `ParameterizedHierBlocks::m_hierSubRun`
(`V3Param.cpp:101-103`) requires that option *in addition to*
`--hierarchical-block`; when it is unset, `findByParams` is never reached and
each instance is de-parameterized into an inlined `magia_tile_hier__<params>`
clone (`V3Param.cpp:1361`). Verilator emits a parameter file only for blocks
with `parameter type` parameters (`V3HierBlock.cpp:282`), and `magia_tile_hier`
has none since Phase 3 replaced its enum-typed parameters with `logic`. No
warning is issued in this path. Fixed by passing
`--hierarchical-params-file verilator/magia_hier_params.v` (deliberately empty;
the option only needs to name a parseable file). It is not in
`stripOptionsForChildRun` (`V3Options.cpp:603-641`), so it propagates from our
stage-1 command line into both generated argument files. Confirmed with
`--debug-exit-elab --debugi-V3Param 9`: all 16 cells now resolve to
`magia_tile_hier_f [VERILATOR-LIB]` instead of cloning.

**2. The Makefile owned a file Verilator owns.** `V<top>.mk` is a *stage-2*
product: `verilator --hierarchical` only writes the plan (its own report says
`into 0.000 MB in 0 C++ files`), and the generated `V<top>_hier.mk` regenerates
`V<top>.mk` by re-running Verilator with `--hierarchical-block`. The old recipe
targeted `V<top>.mk`, asserted it existed right after stage 1, and `touch`ed
it — which can only pass on leftovers, and makes the file look newer than the
child wrapper so the stage-2 rule never fires. The codegen target is now
`V<top>_hier.mk` and nothing here creates, touches or depends on `V<top>.mk`.

Consequence for dependencies: `V<top>__hierVer.d` names `V<top>.mk` as its
target, so it is rewritten into `hierVer.mk` against the owned target. Entries
under the output directory are dropped — the child wrapper is written by stage 2
*after* stage 1 produced its target, so leaving it in makes codegen re-run on
every invocation. The rewrite uses an unconditional `mv`: make re-executes
itself after remaking an included makefile, and a content-compare that leaves
the mtime behind loops forever.

`make -n verilate` is **not** a dry run: the recipe contains `$(MAKE)`,
which GNU make executes even under `-n`, so it starts a real build. Use

### Parent/child ABI mismatch (segfault at time 0)

The first working hierarchical binary segfaulted immediately after the first
heartbeat, in `VlDelayScheduler::nextTimeSlot()` called from the generated
`main`. Cause: `--main` makes Verilator add `-DVL_TIME_CONTEXT` as a side effect
of emitting the main loop (`V3EmitCMain.cpp:45`), and that happens only in the
parent run. The hier_block child library therefore compiled against the legacy
`vl_time_stamp()` time path while the parent used the context path
(`verilated_funcs.h:314,339`) — 458 translation units had `-DVM_TIMING=1` but
only 145 had `-DVL_TIME_CONTEXT`. The two halves disagreed about where
simulation time lives, across the static-library boundary.

This is the same family as Phase 3's Defect 4 (parent-only state not reaching
the child sub-invocation) and is structurally invisible to a flat build.

Fixed with `VERILATOR_ABI_CFLAGS := -DVL_TIME_CONTEXT`, appended to the
`-CFLAGS` passed to Verilator; `-CFLAGS` does reach the child. Kept separate
from `VERILATOR_CFLAGS` because it is a correctness flag, not an optimization,
and recorded in `config.stamp`. Verify with:

```sh
grep 'Vmagia_tile_hier_f' verilator/build/build.log | grep -c VL_TIME_CONTEXT
```

which must equal the child's compile count (312 today). A clean rebuild is
required when changing it: Verilator's generated makefiles do not track
compiler flags, so stale objects would be relinked.

### Functional status

The hierarchical model runs. With deliberately empty stimulus the tiles fetch
from the boot address at 1.086 us and `axi_sim_mem`'s `WarnUninitialized`
reports the accesses, confirming cores, NoC and L2 are live across the
hierarchy boundary.

Hello-world does **not** complete inside the 120 s budget: measured throughput
is roughly 1.2 us of simulated time per wall second (~250 clock cycles/s at the
5 ns period), so a 130 s run reaches about 160 us with no tile output yet. The
`[INFO] X us elapsed in simulation.` heartbeat in `magia_tb.sv` (Verilator-only)
is what makes this measurable. Runtime speed was explicitly out of scope for the
build work; see `verilator/IDEAS.md`. Note the hierarchical model is expected to
be somewhat slower per cycle than a flat one, since Verilator cannot optimize
across the block boundary.

### Waveforms

Tracing is opt-in at build time and again at run time:

```sh
make clean-verilate core=CV32E40P mesh_dv=1
make verilate core=CV32E40P mesh_dv=1 VERILATOR_JOBS=64 VERILATOR_TRACE=1
make verilate-run core=CV32E40P mesh_dv=1 VERILATOR_JOBS=64 \
  test=hello_world VERILATOR_TRACE=1 VERILATOR_FST=dump.fst
```

`VERILATOR_TRACE=1` adds `--trace-fst`; `VERILATOR_TRACE_STRUCTS=1` and
`VERILATOR_TRACE_PARAMS=1` are separate opt-ins under it and error out when
tracing is off. `VERILATOR_TRACE` is part of `config.stamp`, so it must be on
the build command, not only the run command. Rebuild from clean when changing
it: `VM_TRACE`/`VM_TRACE_FST` are compiler flags, which Verilator's generated
makefiles do not track. `magia_main.cpp` is hashed into `config.stamp` and is a
prerequisite of code generation, so editing it does invalidate the build.

Dumping is driven by `verilator/magia_main.cpp`, the maintained simulation main
this flow uses instead of the one `--main` generates. It opens a trace only for
`+FST=<file>`, so a trace-capable model run without the plusarg pays nothing --
not even `traceEverOn`. `VERILATOR_FST` passes the plusarg through
`verilate-run`; the file is written in the test build directory. Verilator
dumps the whole model; there is no scope/level selection.

#### Why the C++ main owns the dump

`magia_tb.sv` deliberately has no `$dumpfile`/`$dumpvars`. A `--hierarchical`
model cannot be traced correctly from an initial block, and getting this wrong
is silent -- the FST is large and perfectly readable, it just has nothing below
`i_magia_tile`.

Each `magia_tile_hier` instance is a protect-library child model. The generated
SV wrapper constructs it through DPI during the *first* evaluation of the
parent, and the child registers its trace callbacks in the shared
`VerilatedContext` only at that point. The parent's own trace registration
emits one `initLib()` lookup per instance
(`Vmagia_tb__Trace__0__Slow.cpp`), matched by scope name against those child
callbacks. So the ordering is fixed: **every child must exist and be connected
before the trace is opened.** `$dumpvars` in an initial block runs inside the
parent's `eval_initial`, before any child is constructed, and its 16 lookups
match nothing.

Do not take child compiler flags as evidence to the contrary. All 441 child
compiles carry `-DVM_TRACE_FST=1` and Verilator emits their
`Vmagia_tile_hier_f__Trace__*.cpp` either way; that proves the trace code was
*generated*, not that it was ever *connected* to the dump. Only the scope tree
of an actual FST proves that -- which is what `verilate-check-fst` exists for.

The main therefore: evaluates once, connects `VerilatedFstC` through
`Vmagia_tb::trace`, opens the file, dumps time zero, and dumps again after each
subsequent evaluation.

The model is constructed as `Vmagia_tb{contextp, "TOP"}` rather than with the
empty name Verilator's generated `--main` passes. This is load-bearing: the
parent builds each lookup key as model-name + `.` + instance path while the
child registers under its wrapper's `$sformatf("%m")`, so an empty name yields
a leading-dot key that matches nothing, the children's trace codes are never
allocated, and the first `dump()` segfaults inside `fstWriterEmitValueChange`.
The visible consequence is that dumped paths start with a `TOP` scope
(`TOP.magia_tb....`), which is Verilator's own convention.

#### Checking a dump

```sh
make verilate-check-fst core=CV32E40P mesh_dv=1 VERILATOR_FST=dump.fst
```

`verilator/check_fst.c` walks the FST hierarchy with the GTKWave `fstapi`
bundled with Verilator -- the same writer's reader -- and fails unless the dump
holds parent signals *and* signals inside all 16 default tile instances. A
relative `VERILATOR_FST` is resolved against the test build directory, the same
way `verilate-run` writes it. Pass `tiles_y tiles_x` to the binary directly for
a non-default mesh.

Do not validate these dumps with tsunami: it byte-swaps wide values on them
(`boot_addr` reads back as `800000cc` instead of `cc000080`). The bundled
`fstapi` gives the correct values.

Cost against the same configuration without tracing:

| | no trace | `VERILATOR_TRACE=1` |
| --- | --- | --- |
| Child / parent C++ files | 310 / 136 | 439 / 192 |
| Generated C++ | 178 + 38 MB | 453 + 94 MB |
| Codegen wall / peak RSS | 1:30.98 / 2.31 GB | 2:09.32 / 2.31 GB |
| Native build wall / peak RSS | 22.17 s / 0.41 GB | 3:19.73 / 0.88 GB |
| Executable / `obj_dir` | 12.5 MB / 692 MB | 51.4 MB / 1.3 GB |
| Simulated time per wall second | ~1.2 us | ~0.7 us |

Once the children are actually in the dump, the file is far bigger than the
old, silently tile-less one: 5,183,100 variables, 319,810 of them per tile,
against the 62,210 recorded in `BUG_REPORT.md`. A 12 us run costs ~20 MB and
runs at ~0.4 us per wall second.

The main closes the trace after `final()` on both normal exits (`$finish` and
running out of events). Let the simulation reach one of them: a run killed by
`VERILATOR_RUN_TIMEOUT` or any signal leaves the FST **unclosed, and an
unclosed FST is not a file you can keep**. `fstWriterCreate` streams the
hierarchy into a `<dump>.hier` companion and only folds it into the FST at
close, so a killed run leaves a `.fst` that is missing its hierarchy plus a
`.hier` beside it that is much larger than the dump itself (109 MB against a
6.4 MB `dump.fst` here). Such a pair still reads -- but only in place; move or
delete the `.hier` and every signal name is gone. A cleanly closed dump is
self-contained and leaves no companion.

To reach `$finish` while the L1 deadlock in `BUG_REPORT.md` is still open, note
that `magia_vip.wait_for_eoc` polls the L2 array at `0xCCFF_0000 + 2*i`, which
`magia_vip.init` clears after preload -- so it has to be written by the program,
but only over the (working) AXI path. Eight hand-assembled instructions that
store the exit code and park, never touching the stack, finish all 16 tiles at
12 us.
